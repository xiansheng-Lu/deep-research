## 1. 目标与范围

M1/M2-2 已交付六阶段链路、冲突裁决 WS 帧与冲突 REST，但看板的实时数据通道只有 `stage.started` 与终态帧：阶段无落库行、子问题/证据仅在事务内 flush 要到 run 终态才对外可见、token 用量只在终态写库、成本预警帧未发出、看板 REST 全部缺失（M2-2 真实链路联调时五个 GET 均 404，已登记于《M2-2批判收敛与人机裁决接口交接》§7.4，明确随 M2-4 处理）。本工作包交付：

1. **M2-4 看板只读接口**：`GET /runs/{id}/stages`、`/sub-questions`、`/evidence`（分页+过滤）、`/evidence/{evidence_id}`（全文懒加载）、`/cost/snapshot`，另增 `GET /runs` 列表（关闭前端方案 R3：首页"进行中研究"卡片不再只靠 localStorage 本地索引）。
2. **Stage 过程数据落库**：六阶段行随运行推进写入与迁移，看板时间线与重连补齐有服务端事实源。
3. **M2-3 实时成本**：`token.usage.update`（1s 节流）与 `cost.warning`（70%/90% 边沿一次）两类 WS 帧；token 用量运行中写穿 `research_runs`，`cost/snapshot` 在 running/paused 态即可读到真实值。
4. **看板增量帧补齐**：`stage.finished` / `stage.failed`、`sub_question.created/started/finished`、`evidence.fetched`，与前端 `frontend/src/services/realtime/types.ts` 已声明类型逐字段对齐。
5. **Metrics Exporter**：新增 `prometheus-client` 与 `GET /metrics`，落《后端详细设计》§12.2 最小指标集；WS 成本帧不走 Prometheus 链路（偏离点见 §10.3）。
6. 冻结 `docs/contract/openapi-m2-4.json` 累积快照（M2-2 快照 15 个路径 + 本批新增 5 个路径 = 20 个路径；`GET /runs` 是既有 `/runs` 路径上的新增方法，不产生新路径对象），与前端完成字段核对后出联调交接单。

- M2-5 的 `pause` / `cancel` / `resume` / `intervene` 写接口与 WS 客户端指令（前端 WP-15 依赖，下一工作包）。
- WS 鉴权切换 Sec-WebSocket-Protocol 子协议：维持 query token（《后端契约草案》§5.3 为已评审预案，切换窗口另定）。
- Redis Pub/Sub 跨进程转发、多 API worker 部署：当前研究任务由 `asyncio.create_task` 在 API 进程内执行，进程内 `RealtimeHub` 已覆盖；跨进程随 Celery 接管（M2-8）处理。
- Pushgateway / Prometheus / Grafana 容器栈与告警：《后端详细设计》§12.4 告警规则标注 M3 起。
- 证据全文 `content` 入库与 MinIO `raw_storage_key` 写入：当前检索链路只保留 500 字 snippet，详情端点的 `content` 本包允许为 null，前端卡片以 snippet 兜底；全文存储另行排期。

- `/projects/{project_id}/runs` 项目维度列表：M3 项目成员模型落地时再开；本包只做创建者维度的 `GET /runs`。

## 5. 关键时序

### 5.1 运行中可见性：super-step 中间提交

现状事务边界为"执行器开事务 → 节点 flush → 终态单次 commit"。看板 REST 与 WS 订阅者分属不同 DB 连接（READ COMMITTED），运行中只能读到终态数据。改造为：

```text
astream 产出 super-step 快照
  → 节点侧 persist_*（session.add / update）
  → 执行器：阶段行迁移 + 成本发射（写 run.token_used）
  → session.commit()        # 每个 super-step 一次
  → WS 帧已在节点/执行器内 publish（队列同进程，不依赖事务）
```

- 全链路约 10~20 个 super-step，提交频次低，无性能问题；
- `sessionmaker` 已配置 `expire_on_commit=False`（见 `app/db/session.py`），提交后 `run` 对象属性不失效，终态 `_mark_*` 续写安全；
- 失败 run 保留中途 stages/sub_questions/evidence（符合 M1"失败可见、不静默"原则，与取消语义"保留中间产物"一致）；
- LangGraph checkpoint 由 `AsyncPostgresSaver` 独立连接池管理，与业务事务不共享，中间提交不影响检查点一致性。

帧与 REST 的竞态口径：节点在 commit 前 publish，客户端收到帧后立即 REST 对齐可能读到旧值（毫秒级窗口）；帧 payload 本身已携带实体可直接渲染，REST 仅补偿，且前端 retrying 期 4s 轮询与 live 后补帧会自愈。不为此引入"提交后发帧"的跨层回调。

### 5.2 成本发射状态机

`RunCostEmitter` 每次 `observe(used, budget)`：

1. `ratio = used / budget`（budget 恒 > 0，仍做除零保护）；
2. **token.usage.update**：距上次发射 ≥ `COST_UPDATE_INTERVAL_MS`（默认 1000ms）即发 `{used, budget}`（本包不带 model_breakdown）；
3. **cost.warning 边沿**：内部 level 状态机 `None → warning(ratio ≥ 0.70) → danger(ratio > 0.90)`，每级至多发一次；若用量单跳越过 0.90，只发 danger（不补 warning）；
4. **写穿**：节流节奏内同步 `run.token_used = used`，随 §5.1 的 super-step commit 对 REST 可见；
5. `force=True`（终态/挂起点）无视节流补发最后一帧 token.usage.update，保证收尾数字与 run 行一致。

阈值与 `edges.decide_after_cost_checkpoint` 共用 `COST_DANGER_RATIO`，保证"变红"与"挂起闸门"同源。danger 帧在 cost_checkpoint super-step 后、挂起提交前发出，前端在 paused 引导出现前即可看到红色成本卡。

### 5.3 重连补齐（不做服务端帧回放）

《后端详细设计》§8.3 的断连补齐路径为"重连后先拉 cost/snapshot 再订阅 WS"。前端 `useRunStream.alignWithRest` 已按此实现：live 后并发拉 run/stages/sub-questions/conflicts/cost/evidence 第一页，404 各自静默。本包端点全部就绪后该机制自动生效，**WS 不做订阅时帧回放**，M1 已知边界"WS 不回放订阅前事件"由这套 REST 快照正式关闭。事件去重沿用 envelope 的 `event_id` + 前端稳定 key 合并。

## 6. REST 契约（本批新增，冻结于 openapi-m2-4.json）

通用约定沿用《后端详细设计》§4.1：除列表过滤参数外鉴权同 M1；非创建者/不存在统一 404（401 为无/坏 token）；时间 ISO 8601 UTC。

| 方法与路径 | 查询参数/响应 | 说明与排序 |
| --- | --- | --- |
| GET `/api/v1/runs` | `status?`（六态枚举，可重复值先只支持单值）、`project_id?`、`page=1`、`page_size=20`(≤100) → `PageEnvelope<RunResponse>` | 创建者维度强制 `creator_id=当前用户`；project_id 再过滤且校验团队归属（非本团队项目返回 404，不泄漏项目存在性）；`created_at DESC`；解决前端方案 R3 |
| GET `/api/v1/runs/{run_id}/stages` | → `StageResponse[]` | 固定六阶段顺序返回；run 创建于本包上线前的历史 run 返回空数组（前端 `mapStages` 以 run.current_stage 推导兜底） |
| GET `/api/v1/runs/{run_id}/sub-questions` | → `SubQuestionResponse[]` | `created_at ASC` |
| GET `/api/v1/runs/{run_id}/evidence` | `page=1`、`page_size=20`(≤100)、`sub_question_id?`、`include_excluded=false` → `PageEnvelope<EvidenceResponse>` | 默认剔除 `excluded_by_user=true`（《后端详细设计》§5.5.2）；`fetched_at DESC, id ASC` 稳定次序；sub_question_id 过滤时校验归属同一 run |
| GET `/api/v1/runs/{run_id}/evidence/{evidence_id}` | → `EvidenceResponse` | 全文懒加载通道（承接前端 mock 先行路径，见 §10.5）；归属不符 404；`content` 本包通常为 null |
| GET `/api/v1/runs/{run_id}/cost/snapshot` | → `CostSnapshotResponse` | 见下；running/paused/succeeded 均可读 |

分页信封（改造后的 `PaginatedResponse[T]`，扁平对齐《后端详细设计》§4.1.4）：

```json
{ "items": [...], "total": 37, "page": 1, "page_size": 20, "has_more": true }
```

`StageResponse`：`id, run_id, name, status, attempt, started_at, finished_at, created_at, updated_at`（不输出 Stage 行的 token_used/error_code/output——token 在成本域，失败原因走 `stage.failed` 帧与 run 详情；与前端类型逐字段一致）。

`SubQuestionResponse`：`id, run_id, question, depends_on, status, evidence_count, created_at, updated_at`。

`EvidenceResponse`：`id, run_id, sub_question_id, url, domain, title, snippet, content(nullable), source_type, source_level, credibility, relevance_score, published_at, fetched_at, excluded_by_user, created_at, updated_at`。

`CostSnapshotResponse`：

```json
{ "used": 108320, "budget": 150000, "ratio": 0.722, "level": "warning" }
```

`level` 按同一阈值派生：`ratio > 0.90 danger`、`≥ 0.70 warning`、否则 `null`（字段保留可空，前端成本卡自行按 ratio 上色，level 供未来直接消费）；不输出 model_breakdown。

错误码：沿用现有异常体系——无 token 401；资源不存在/不归属 404 NotFoundError；非法 status 枚举/分页越界 422（FastAPI/Pydantic 标准校验响应）。

## 7. 实时帧契约（不入 OpenAPI，沿用 envelope）

外层结构由 `app/realtime/ws.py::_make_envelope` 统一包装（v/event_id/ts/run_id/stage/type/payload）；下列仅约定 type 与 payload，全部与前端 `realtime/types.ts` 已声明形态一致。

| type | 时机 | payload |
| --- | --- | --- |
| `stage.finished` | 阶段切换时旧阶段收口（终态 report 收口同样发） | `{stage, attempt, status:"succeeded", duration_ms, token_used}` |
| `stage.failed` | run 失败终态，定位到 current_stage | `{stage, attempt, status:"failed", error_code, error_message, retryable:false}` |
| `sub_question.created` | decompose 落库后逐条 | `{sub_question_id, question, status:"pending", depends_on:string[]}` |
| `sub_question.started` | retrieve 每层调度前逐条 | `{sub_question_id, status:"running"}` |
| `sub_question.finished` | retrieve 每层结果落库后逐条 | `{sub_question_id, status, evidence_count}`（status ∈ running 后的终态：succeeded/failed/evidence_short） |
| `evidence.fetched` | standardize 新证据落库后逐条 | EvidenceResponse 展示子集：`id, sub_question_id, url, domain, title, snippet, source_type, source_level, credibility, relevance_score, published_at, excluded_by_user` |
| `token.usage.update` | super-step 中 used 变化且距上帧 ≥1s；终态强制一帧 | `{used, budget}` |
| `cost.warning` | ratio 跨越 70%/90% 边沿，每级一次 | `{level:"warning"|"danger", used, budget, ratio}`（《后端契约草案》§4.2 定版） |

约束：

- 帧发布一律 try/except 吞错只告警，不阻断研究主链（hub 缺省/推送失败语义同 `conflict.detected`）。
- 证据帧不做服务端定时节流：《后端详细设计》§4.3.1 表中 500ms 节流由前端 `queueEvidence` 的 requestAnimationFrame 合批承接；服务端保持"落库即发"的简单语义，避免缓冲层丢/重复杂度。
- `sub_question.*` 与 `evidence.fetched` 只在真实落库成功后发，保证帧内实体随后的 REST 一定可查到（§5.1 毫秒级竞态除外）。
- 现有 `stage.started` / `run.finished` / `run.failed` / `conflict.*` 载荷不变。

## 8. 数据模型与迁移

- 不新增表、不新增列；仅 0003 给 `stages` 加 `uq_stages_run_name (run_id, name)` 唯一约束。
- 该约束是 upsert 幂等与恢复重放的前置；存量数据中 stages 为空表，升级无数据冲突风险。
- Stage 行语义：
  - run 启动：6 行 pending；
  - 进入阶段：running + started_at + attempt（attempt 取 state.stage_attempts，默认 1）；
  - 切出/成功：succeeded + finished_at + token_used（该阶段收口快照值）；
  - run 失败：current_stage 行 failed + error_code，后续阶段保持 pending；
  - run 挂起（澄清/裁决/成本）：current_stage 行保持 running（暂停语义由 `research_runs.status=paused` 承载，Stage 枚举无 paused）；
  - 恢复续跑命中已完成阶段：upsert 不回退已 succeeded 的行。

## 9. Metrics Exporter（M2-3 运维面）

新增依赖 `prometheus-client`（《后端详细设计》§7.7/§12.2 已选型，pyproject 目前仅有 opentelemetry 系列）。

落位：

- `app/observability/metrics.py`：模块级全局单例 collector（不在 `create_app` 内重复构造，避免测试多 app 实例 `Duplicated timeseries`），导出：

## 10. 与 LLD / 契约草案的偏离点

1. **成本帧发射点**：《后端详细设计》§6.5.8 示意由 cost_checkpoint 节点内 `event_bus.publish` 发 cost.warning，且只在审视后一次检查。本方案保持 cost_checkpoint 为纯 state 节点，发射集中到执行器驱动循环内的 `RunCostEmitter`：预警在任意阶段跨越阈值即可发出（token 在 clarify/decompose/critique 都可能增长），同时免去纯节点改 deps 注入的图接线改动；90% 挂起路由仍由原条件边负责，阈值共用常量。
2. **evidence.fetched 时机**：LLD 事件表语义为检索到即推（retrieve 阶段）。本方案在 standardize 分类落库后推送：retrieve 期证据带临时分级（tertiary/C），《M2-2 技术方案》已确立"临时分级不固化"原则，帧与 DB 同源可避免看板先渲染 C 级再跳级；代价是证据流在 standardize 超步集中出现（前端 rAF 合批承接，且本阶段距 run 结束很近）。
3. **WS 成本链路不经 Pushgateway/Prometheus**：《后端详细设计》§7.7 的链路为 Provider → Pushgateway → Prometheus → Exporter(5s PromQL) → EventBus → WS。该链路仅 Exporter 轮询间隔就接近 A5 的 ≤3s 预算，且要求本地开发具备 Prometheus 栈。本方案运行态成本以 ResearchState 为唯一事实源，经进程内 Hub 直推 WS（亚秒级），Prometheus 只承担运维面拉取（§9）；研究任务改由 Celery Worker 执行（M2-8）后，Worker 侧计数再经 Pushgateway 推送，届时 Prometheus 仍不反向承载 UI 实时帧。
4. **分页信封形态**：《后端详细设计》§4.1.4 与《后端契约草案》§3 均为扁平 `{items,total,page,page_size,has_more}`，仓内 `PaginatedResponse` 现为 `{items,meta{...}}` 且零消费方；直接扁平改造，不保留双形态。
5. **单条证据详情路径**：《后端详细设计》§4.2.5 只列证据池分页，未列单条端点；前端 mock 先行已按 `GET /runs/{id}/evidence/{evidence_id}` 实装并隔离在 `dashboard.ts::getEvidence` 单函数内。本方案确认该嵌套路径为正式契约（归属校验天然复用 run 归属），不另设顶级 `/evidence/{id}`。
6. **run 列表端点形态**：《后端详细设计》§4.2.4 列的是项目维度 `GET /projects/{project_id}/runs`（依赖项目成员模型，M3）。首页"进行中研究"跨项目卡片（前端方案 R3）本包需要数据源，先落创建者维度 `GET /runs`（与现有 `GET /runs/{id}` 的 creator 归属口径一致），项目维度端点 M3 随成员模型再开，两不冲突。
7. **WS 不做服务端初帧回放**：M1 遗留"订阅前事件丢失"由 stages/sub-questions/evidence/cost 四个快照端点 + 前端 live 后 `alignWithRest` 关闭，不在 WS 连接建立时回放历史帧（《后端详细设计》§8.3 的断连补齐本就指向 REST 快照路径）。
8. **StageResponse 不输出 error_code/token_used/output**：表中有列但前端时间线类型未声明；失败原因走 `stage.failed` 帧与 run 详情，阶段 token 走成本域，避免一字段三处口径。后续若 WP 需要再按契约变更走 OpenAPI diff。

### 15.4 与前端的核对结论（AC-19）

- 已只读核对 `frontend/src/services/api/types.ts`：StageResponse（无 token_used/error_code）、EvidenceResponse（content nullable、excluded_by_user、无 fingerprint/metadata）、扁平分页信封、查询参数均一致。
