# AI 研究者助手 · 智能体协作规格说明

> **文档性质**：HLD（高层设计）类基线文档，与 [PRD](../prd/AI研究者助手-软件需求规格说明书.md) 平级。
> 描述"由哪些智能体、按什么契约协作、上下文如何隔离、失败如何回溯"，是 6 阶段研究流程的实现蓝图。
>
> **变更原则**：Agent 角色列表变更（新增/删除/合并）需同步通知 PRD 维护方评估对需求基线的影响；Agent 内部实现细节调整无需升版 PRD。

---

## 1. 协作范式总览

主链采用**严格流水线**：上游→下游按阶段推进。

- **阶段 3（并行检索）** 内部存在**扇出**（按子问题并行），是唯一的并行区
- **阶段 5（批判收敛）** 内部存在**迭代收敛**，是唯一的循环区
- **阶段 3↔4 之间** 允许"证据不足 → 回溯"的有限循环
- **没有全局共享的"主管 Agent"**——避免单点瓶颈与协调开销

编排层（Orchestrator）跨阶段负责依赖、回溯、降级与暂停决策；各业务 Agent 只管好自己契约内的输入输出，不越界。

```mermaid
graph LR
    IR["意图路由 Agent"] --> CL["澄清 Agent<br/>(阶段1)"]
    CL --> PA["规划 Agent<br/>(阶段1)"]
    PA --> SQ["子问题拆解 Agent"]
    SQ --> RA["检索 Agent × N<br/>(子问题并行)"]
    RA --> ST["标准化 Agent"]
    ST --> CR["批判 Agent<br/>(多轮收敛)"]
    CR --> RG["报告生成 Agent"]
    RG --> RP["报告呈现层<br/>(前端组件)"]
```

## 2. Agent 角色清单

研究流程共 **8 类 Agent**（含意图路由）+ **3 类横切模块**（编排、成本守门、审计日志）。

| # | Agent | 所属阶段 | 部署方式 | 上下文范围 |
|---|---|---|---|---|
| 1 | 意图路由 Agent | 入口 | 单实例 | 用户单条输入 |
| 2 | 澄清 Agent（Clarifier） | 阶段1 | 单实例 | 当前问题会话 |
| 3 | 规划 Agent（Planner） | 阶段1 | 单实例 | 当前问题会话 |
| 4 | 子问题拆解 Agent（SubQuestioner） | 阶段2 | 单实例 | 当前研究 |
| 5 | 检索 Agent（Researcher） | 阶段3 | **N 实例并行**（每子问题 1 个） | **独立上下文**（不共享） |
| 6 | 标准化 Agent（Standardizer） | 阶段4 | 单实例 | 全局证据池 |
| 7 | 批判 Agent（Critic） | 阶段5 | 单实例迭代 | 全局证据池 |
| 8 | 报告生成 Agent（Reporter） | 阶段6 | 单实例 | 全局结论集 |

横切模块（与业务 Agent 并行运行）：

- **Orchestrator（编排层）**：监测阶段间依赖、触发回溯、降级与暂停
- **CostController（成本守门）**：监听实时 token 消耗，达档位上限触发告警/降级
- **AuditLogger（审计日志）**：记录阶段关键决策，形成可回放轨迹

## 3. 各 Agent 详细规格

### 3.1 意图路由 Agent
- **角色**：入口分流，判别"闲聊/研究/不确定"
- **输入**：用户原始问题 + 用户上下文
- **输出**：意图分类 + 置信度 + 推荐参数（默认模板、默认档位）
- **能力**：基于问题长度、具体性、关键词、是否需多源验证打分
- **不做**：检索、报告生成、保存到研究项目
- **降级**：判别超时或失败时默认走"研究"路径并显式说明

### 3.2 Clarifier 澄清 Agent
- **角色**：把模糊问题变成结构化研究问题
- **输入**：用户原始问题 + 可选上下文
- **输出**：结构化问题对象（目标、范围、关键概念、约束）
- **能力**：识别"信息不足"主动回问；判断何时停止澄清（最多 1 轮回问）
- **不做**：检索、报告草稿、推测研究结论

### 3.3 Planner 规划 Agent
- **角色**：基于模板与澄清后问题生成研究骨架参数
- **输出**：默认模板建议、默认深度档位、参数建议（含成本预估）
- **与意图路由对接**：路由给出推荐参数，规划 Agent 在用户确认后落地

### 3.4 SubQuestioner 子问题拆解 Agent
- **角色**：拆解为尽量独立的子问题，标注依赖
- **输入**：结构化问题 + 模板
- **输出**：子问题列表 + 依赖图（节点=子问题、边=依赖）
- **关键约束**：子问题默认不依赖；确实需要依赖则显式标注，运行时由编排层据此动态排队
- **不做**：检索、不评估"够不够"、不写答案

### 3.5 Researcher 检索 Agent（核心并行区）
- **部署**：每个子问题 1 个 Researcher 实例，子问题并行；每个 Researcher 内部**多路线并行**（综合搜索、官方源、专业 API、社区）
- **输入**：单个子问题 + 档位参数（轮次上限、token 配额）
- **输出**：子问题证据池（原始网页/文档 + 元数据）
- **能力**：迭代追问下钻；档位决定追问轮次上限
- **不做**：跨子问题去重（交标准化 Agent）、不下结论（交批判 Agent）
- **上下文管理**：自带独立上下文窗口，不共享；超出档位配额自动收尾

### 3.6 Standardizer 标准化 Agent
- **角色**：跨子问题统一清洗证据
- **输入**：所有子问题证据池
- **输出**：标准化材料池（含来源域名、发布时间、信源类型、可信分级、去重打分、相关性分）
- **能力**：去重合并、元数据补全（缺失项标注"来源信息不全"）、按可信度排序、给每条证据打指纹
- **不做**：判断证据真假（这是批判 Agent 的事）、不生成结论
- **关键位置**：唯一能看到**所有**子问题证据的 Agent，承担"跨子问题合并证据"的角色，为阶段5 提供"证据簇"雏形

### 3.7 Critic 批判 Agent
- **角色**：质疑与收敛
- **输入**：标准化材料池 + 报告骨架预对齐产物
- **输出**：已收敛结论集 + 显式分歧集 + 报告骨架
- **能力**：
  - 可调和冲突：通过多源对比、合理论证收敛成单一结论
  - 不可调和冲突：标注分歧、保留各源、显式呈现给用户
  - 批判维度：事实正确性、来源可信、时效、立场偏向、推理有效性
- **收敛机制**：迭代运行；达档位 token 预算 x%（默认 30，`[待确认]`）即停
- **不做**：写报告散文、润色、生成可视化

### 3.8 Reporter 报告生成 Agent
- **输入**：阶段5 产物（收敛结论 + 显式分歧 + 报告骨架）
- **输出**：在线交互式报告
- **能力**：按模板生成"**结论/证据/分歧/局限**"四类区块；每个论断自动绑定溯源组件
- **关键约束**：任何论断必须绑定信源，缺源即降级为"推断"标记

### 3.9 报告呈现层（前端组件）
- 非 Agent，是与 Reporter 解耦的前端层
- 提供：点击论断回溯原文、筛选分歧、可视化证据时间线/可信分级、导出结构化字段
- 与 Reporter 的契约：渲染数据格式（建议 JSON Schema 化）需提前约定

## 4. 横切模块

### 4.1 Orchestrator 编排层
- **职责**：监测 Researcher 输出；发现"证据不足"→触发回溯（追加轮次或反馈到拆解阶段）；检测到新依赖→把后置子问题挂起到前置结论产出
- **位置**：跨阶段运行，不属于单一阶段
- **决策原则**：失败不回退到用户时，先尝试自动回溯；若预设策略耗尽仍未收敛，暂停并请用户决策

### 4.2 CostController 成本守门
- **职责**：跨阶段监听每项研究的实时 token 消耗
- **触发**：达档位上限 → 降级提示 / 用户预算警告
- **与看板对接**：实时 token 消耗展示
- **不参与决策**：仅提供数据与触发信号，研究路径选择仍由 Orchestrator 与用户决定

### 4.3 AuditLogger 审计日志
- **职责**：记录每阶段关键决策（澄清假设、子问题划分、检索轮次、批判结论变更）
- **产物**：可回放的研究轨迹
- **喂给**：溯源 UI 与报告的"局限/置信"区块
- **存储**：与项目绑定，独立于业务数据可追溯

## 5. 协作契约（接口与边界）

### 5.1 通用边界原则
- 每个 Agent 边界严格：输入/输出/不做的事写在 prompt 与接口契约里
- 不允许跨边界：Researcher 不下结论、Critic 不润色散文、Clarifier 不检索
- 上下文分层管理：避免污染与超限（详见 §6）

### 5.2 阶段间契约表

| 上游 Agent | 下游 Agent | 契约（输入约定） | 失败处理 |
|---|---|---|---|
| 意图路由 | Clarifier / Planner | 意图分类 + 推荐参数 | 路由失败默认走研究 + 显式说明 |
| Clarifier | Planner | 结构化问题对象 | 1 轮回问超时默认假设，标注假设项 |
| Planner | SubQuestioner | 模板 + 档位 + 结构化问题 | — |
| SubQuestioner | Researcher × N | 子问题列表 + 依赖图 | 依赖图冲突由 Orchestrator 动态排队 |
| Researcher | Standardizer | 子问题证据池 | 证据不足触发 Orchestrator 回溯 |
| Standardizer | Critic | 标准化材料池 | 元数据缺失标注"来源信息不全" |
| Critic | Reporter | 收敛结论 + 分歧集 + 骨架 | 达收敛上限即停，残余分歧显式呈现 |
| Reporter | 报告呈现层 | 报告渲染数据（JSON Schema 化） | 缺源论断降级为"推断" |

## 6. 上下文管理

| Agent | 上下文范围 | 大小控制 |
|---|---|---|
| 意图路由 / Clarifier / Planner | 单条问题会话 | 自然受会话长度限制 |
| SubQuestioner | 当前研究 | 子问题数量受档位约束 |
| Researcher × N | **完全独立**（关键） | 档位 token 配额为硬上限 |
| Standardizer / Critic / Reporter | 全局证据/结论 | 通过标准化材料池的"摘要+引用"压缩 |

**核心原则**：Researcher 上下文**完全隔离**——避免一个子问题的失败污染其他子问题；也避免 token 累积导致单实例超限。

## 7. 失败与回溯策略

| 失败类型 | 检测者 | 默认动作 | 兜底 |
|---|---|---|---|
| 信息不足（阶段1） | Clarifier | 主动回问（≤1 轮） | 超时默认假设，标注假设项 |
| 子问题依赖冲突（阶段2→3） | Orchestrator | 动态排队（后置等前置） | 重跑 SubQuestioner |
| 证据不足（阶段3→4） | Standardizer | 触发 Researcher 追加 | 多次追加仍不足→标注"证据不足" |
| 批判不收敛（阶段5） | Critic | 达 token 预算 x% 即停 | 残余分歧显式呈现给用户 |
| 报告缺源（阶段6） | Reporter | 论断降级为"推断"标记 | 不冒充事实 |
| 路由超时（入口） | 意图路由 | 默认走"研究" | 显式说明 |

**核心原则**：
- 失败不静默——必须显式呈现给用户
- 不无限循环——所有循环都有硬上限（轮次或 token 预算）
- 用户有权暂停与干预——通过 Orchestrator 暴露的暂停接口

## 8. 可测试性

每个 Agent 都具备独立测试能力：

- **单测**：给输入看输出是否符合契约（输入/输出/不做的事）
- **集测**：看与上下游对接是否顺畅（契约一致、字段兼容）
- **端到端测试**：通过验收清单 A1~A14 覆盖（详见 PRD）

调优单一 Agent 不影响全局；新增/删除 Agent 需同步更新 §2 角色清单与 §5 契约表。

## 10. 交互协议

Agent 之间的"怎么说话"——消息契约、调用方式、超时与失败处理。本章与 §5 协作契约互为表里：§5 描述"传什么字段"，本章描述"怎么传、何时算成功、何时算失败"。

### 10.1 四种交互模式

| 模式 | 形态 | 典型场景 | 核心约束 |
|---|---|---|---|
| 请求-响应 | 同步阻塞 | Clarifier → Planner、Critic 调 Reporter 出草稿 | 必传上下文摘要、不传原始证据；超时重试 |
| 扇出-聚合 | N 个并行实例 → 1 个聚合者 | SubQuestioner → Researcher × N → Standardizer | 实例独立上下文；聚合支持部分完成；heartbeat 上报 |
| 迭代收敛 | 单实例内部多轮 | Critic 内部多轮质疑；Critic → Researcher 补查 | 三类收敛信号（正向/预算/轮次）；补查开新实例不破坏可重放 |
| 用户介入 | 经 Orchestrator 中转 | 阶段1 回问、阶段3 暂停、阶段5 打回 | 用户不直接修改 Agent 状态；通过受控操作触发 |

### 10.2 请求-响应模式

**调用方式**：同步阻塞，上游 Agent 发起后挂起，等待下游返回；编排层是协调者。

**消息格式契约**：
- `task_id`：本次请求的唯一标识，用于链路追踪
- `caller` / `callee`：调用方与被调方
- `payload`：上游传来的输入（结构化）
- `constraints`：硬约束（截止时间、token 上限、必须遵守的规则）
- `context_snapshot`：上游上下文的可读摘要（不是全量上下文），避免下游污染
- `callback`：超时或失败时的回调策略

**超时与重试**：
- 默认超时按档位定：快速 10s / 标准 30s / 深度 60s / 极致 120s（`[待确认]`）
- 重试最多 1 次，第二次失败直接升级到 Orchestrator
- 重试时携带 `previous_error`，让下游调整策略

**关键点**：上游给下游的是**上下文摘要而非全量**。否则上下文会逐级放大，到 Critic 时已经爆掉。

### 10.3 扇出-聚合模式

**调用方式**：编排层一次性把所有子问题派发给 N 个 Researcher，每个 Researcher 是独立进程/任务；N 个 Researcher **互不感知，不共享中间结果**。

**聚合策略**：
- 默认等待全部完成（slow but complete）
- 达到 `wait_threshold`（如 80% 子问题完成）后开启快速通道，先聚合已完成的让 Critic 启动
- 落后子问题作为"未完成项"在报告中显式标注

**进度回报**：每个 Researcher 每完成 1 轮追问就回报 1 次 heartbeat，喂给看板实时刷新。心跳内容为"轻量摘要"（在查什么/查到几条/来自哪些源），不暴露原始证据原文。

### 10.4 迭代收敛模式

**自循环**：Critic 给自己的迭代不需要走"上游→下游"模式，而是单实例内部的多轮调用。

**三类收敛信号**（任一触发即停）：
- **正向收敛**：本轮新增结论 < 阈值（如 5%）→ 停止
- **预算收敛**：累计消耗达到档位 token 预算 x%（默认 30）→ 停止
- **轮次收敛**：达到最大轮次（如 3 轮）→ 停止

**外呼补查**：Critic 发现某条结论需要更多证据时，可发起"补查请求"回 Researcher：
- 是**新开**一个 Researcher 实例（不打断原检索），并行补查
- 必须显式标注"这是补查，原结论 X 需要证据 Y"
- 补查完成后 Critic 重新评估该结论并更新状态

**关键点**：Critic 不能修改 Researcher 的输入（避免破坏检索的不可重复性），只能开新实例补查。这保证研究过程可追溯、可复现。

**分歧显式化**：当 Critic 判断"该冲突不可调和"时，**不再尝试收敛**，转为输出分歧集（保留各源 + 立场判定）。

### 10.5 用户介入模式

**介入接口**：用户操作通过 Orchestrator 中转，**不直接修改 Agent 状态**。

**介入点**（每个阶段都允许）：
- 阶段1：回问澄清
- 阶段3：暂停 / 追加追问方向 / 剔除某条证据
- 阶段5：对收敛结论打回重审（附带原因）
- 阶段6：对论断标"存疑"，触发 Reporter 重新评估该条

**暂停语义**：
- **软暂停**：Agent 完成当前原子操作后停下（不打断中间推理）
- **硬暂停**：立即中断当前 Agent（仅在 token 告警等紧急场景）

**权限边界**：用户不能直接修改 Agent 内部 prompt，只能触发"重跑/追问/剔除"等受控操作。

**关键点**：用户是"业务决策者"，不进入"模型调用方"。所有模型调用都通过 Orchestrator 调度，避免用户操作绕过审计与回溯。

### 10.6 五条通用交互规则

适用于上述四种模式，是底层不变式：

1. **消息可追溯**：每次交互都带 `task_id` + `parent_task_id`，形成 DAG，可重放
2. **失败显式化**：任何超时或异常都返回结构化错误（含错误码、错误描述、可恢复性），不静默
3. **上下文隔离**：默认只传"摘要+引用"，不传原始证据原文
4. **限流与背压**：当某 Agent 队列超过阈值，编排层启用背压（拒绝新任务并提示用户）
5. **幂等性**：相同 `task_id` 的重试必须幂等，不能因为重试产生重复证据或重复结论
