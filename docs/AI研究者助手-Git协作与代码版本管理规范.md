# AI 研究者助手 · Git 协作与代码版本管理规范

> 版本: v1.1 · 生效日期: 2026-09-09 · 适用范围: 全项目（M1-M3 及后续迭代）
> 适用角色: 开发（前端/后端）、产品、设计 · 上游依据: SDP《软件开发计划》
> 目标: 支撑前后端并行开发与多角色协作场景下的文件变更管理，保障代码库整洁、可追溯、协作高效

---

## 1. 概述

### 1.1 目标

1. 建立清晰的分支管理策略，支持前后端并行开发、功能独立演进、稳定发布与快速修复。
2. 规范提交信息格式与内容质量，保证历史可读、可检索、可审计。
3. 明确评审与合并流程，把控代码质量与协作节点。
4. 固化版本号管理规则，支撑发布、回滚与上下游契约对齐。
5. 明确开发/产品/设计三类角色的文件职责边界与提交流程，避免越权覆盖和无序冲突。

---

## 2. 仓库结构约定

当前仓库采用分层目录组织，各目录角色责任固定：

| 目录 | 责任角色 | 说明 |
| --- | --- | --- |
| `backend/` | 开发（后端） | Python3.11 + FastAPI + uv 服务端 |
| `frontend/` | 开发（前端） | Vue3 + Vite + pnpm 客户端 |
| `docs/prd/` | 产品 | 需求规格说明书 |
| `docs/plan/` | 产品 | 软件开发计划 |
| `docs/design/` | 设计（为主）、开发 | 架构、前后端详细设计、交互/契约/智能体规格 |
| `prototype/` | 设计、产品 | 前端高保真原型页面 |
| `.gitignore` 等根级文件 | 开发（公共） | 仓库级配置，变更需全角色周知 |

角色范围之外的目录原则上不出现在该角色的 MR/PR 中，确需修改时在描述中说明原因。

## 3. 分支管理策略

### 3.1 分支类型与命名规则

| 分支类型 | 命名规则 | 示例 | 生命周期 | 权限 |
| --- | --- | --- | --- | --- |
| 主分支 | `main` | `main` | 长期 | 只读，禁止直接 push，仅经 MR 合并 |
| 开发分支 | `develop` | `develop` | 长期 | 只读，禁止直接 push，仅经 MR 合并 |
| 功能分支 | `feature/{说明}` | `feature/research-pipeline` | 任务完成即删除 | 各角色自行创建与维护 |
| 发布分支 | `release/{版本号}` | `release/v1.0.0` | 发布后删除 | 受限，仅 release manager |
| 修复分支 | `bugfix/{说明}` | `bugfix/report-404` | 修复合并后删除 | 开发 |
| 紧急修复分支 | `hotfix/{版本号}` | `hotfix/v1.0.1` | 修复合并后删除 | 开发（紧急） |

命名补充约定：

- 小写字母与数字，单词以 `-` 分隔，避免中文、空格、`_` 混用带来的跨平台问题。
- 分支名应能短化概括改动意图，如 `feature/crm-data-connector`。
- 同一大功能前后端并行时，允许按端二次划分，如 `feature/research-pipeline-frontend` 与 `feature/research-pipeline-backend`；若必须共享契约改动，应在 MR 描述互相引用以保持同步。
- 文档/原型类变更使用 `feature/{角色}-{说明}`，如 `feature/design-interaction-spec`、`feature/proto-knowledge-page`。

### 3.2 分支流向

- 主流程：`feature/* → develop` 集成，`develop → release/vX.Y.Z → main` 发布。
- 紧急修复：`hotfix` 从 `main` 拉出，合并回 `main` 与 `develop`。

### 3.3 分支使用规范

1. 从正确的基分支拉取：功能分支一律从 `develop`（或经批准的 `release`）拉取，修复分支从对应的发布/主分支拉取。
2. 分支应只在创建者与协作范围内使用，完成并合并后及时删除，避免分支堆积。
3. 禁止将禁用命令/破坏性操作作用于共享分支（详见 §10.1）。

## 4. 提交信息格式标准

采用约定式提交（Conventional Commits），保证日志可检索、可自动生成变更记录。

### 4.1 格式

```
<type>(<scope>): <subject>

<body>
```

- `<type>`: 必填，提交类型（见 §4.2）。
- 破坏性变更：在 type 后追加 `!`（如 `feat!:`）或在 body 中写入 footer `BREAKING CHANGE:`，触发 MAJOR 版本提升（见 §7）。
- `<scope>`: 可选，影响范围，使用目录或模块名，如 `backend`、`frontend`、`prd`、`design`、`proto`。
- `<subject>`: 必填，一句话摘要，不超过 72 字符，使用祈使句、中文陈述，不以句号结尾。
- `<body>`: 可选，补充无法在一行内说明的背景、原因与影响，可分行列出要点（以 `- ` 开头）。

### 4.2 提交类型（type）

| 类型 | 含义 | 常见使用角色 |
| --- | --- | --- |
| `feat` | 新增功能 | 开发、设计、产品 |
| `fix` | 缺陷修复 | 开发 |
| `docs` | 仅文档变更 | 产品、设计、开发 |
| `style` | 不影响逻辑的格式/样式调整 | 开发 |
| `refactor` | 重构但无功能/缺陷变化 | 开发 |
| `perf` | 性能优化 | 开发 |
| `test` | 测试相关 | 开发 |
| `build` | 构建/依赖变更 | 开发 |
| `ci` | CI 配置变更 | 开发 |
| `chore` | 维护性杂项（目录骨架、配置等） | 开发 |
| `design` | 交互/视觉/原型设计产出 | 设计 |

### 4.3 提交示例

```
docs(prd): 补充研究报告导出格式需求

- 新增导出 PDF/Markdown 的格式与字段说明
- 明确页眉、章节编号与会签名格式
```

```
feat(frontend): 驾驶舱支持研究进度实时展示
```

```
chore: 初始化 backend、frontend 目录骨架
```

### 4.4 质量标准

1. 一次提交只做一件事，逻辑内聚，便于回滚与评审。
2. 提交信息必须能独立说明"为何改、改了什么"，拒绝 `update`、`fix some` 之类的空泛描述。
3. 涉及跨端契约（后端 API、前端对接）联动改动时，在前端提交 body 中引用对应后端提交/契约文档，保证可追溯。
4. 文档与代码混改时拆分为多条提交（`docs` 与 `feat`/`fix` 分开），便于溯源。

## 5. 合并策略

### 5.1 合并方式选择

| 场景 | 推荐策略 | 说明 |
| --- | --- | --- |
| 功能分支 → develop | Squash Merge | 仅保留一条汇总提交，历史简洁；feature 内部提交可粗略 |
| 修复分支 → develop | Squash 或 Fast-forward | 保持修复记录单一清晰 |
| hotfix → main | Merge, `--no-ff` | 保留紧急修复节点，便于追溯 |
| hotfix → develop | Merge, `--no-ff` | 保证 develop 承接线上修复，避免回归缺失 |
| release → main | Merge, `--no-ff` | 保留发布节点结构，便于回看发布边界 |

### 5.2 合并前置条件

1. 分支最新：合并前先同步目标分支最新代码，本地验证通过。
2. MR/PR 通过评审（见 §6）。
3. 无未解决的冲突（冲突处理见 §8）。
4. 通过质量门槛：原型/Docs 类至少人工审阅；代码类须通过构建与必要的测试。

### 5.3 合并后动作

- 合并后的 feature/bugfix/hotfix 分支立即删除。
- 若开启了 release，发布后删除对应 release 分支。
- 更新 milestone/标签与《软件开发计划》中的进度记录（由对应角色执行）。

## 6. 代码审查流程

### 6.1 触发时机

所有合并到 `develop`、`release`、`main` 的变更，原则上必须通过 MR/PR 评审；紧急 hotfix 可先合并后补审并在描述中标注。

### 6.2 评审角色与职责

| 角色 | 参与方式 | 职责 |
| --- | --- | --- |
| 提交者（Author） | 发起 MR/PR | 提供完整描述、验证改动、回复评审意见 |
| 评审者（Reviewer） | 评审 | 检查正确性、可维护性、质量与契约一致性 |
| 集成/发布负责人 | 验收 | 把控发布边界、版本号、变更记录 |

评审者建议由相关角色交叉担任：后端改动评审角色含后端开发者与后端契约引用者；前端改动评审角色含前端开发者与接口调用方；文档/原型改动评审角色含产品/设计负责人及对应用途的使用者。

### 6.3 评审检查项（Checklist）

1. 改动范围与 MR 描述一致，无越权文件。
2. 提交信息规范、改动拆分合理。
3. 功能正确、命名清晰、注释为简体中文（如有）。
4. 无死代码、无重复造轮子（遵循"不重复造轮子"原则）。
5. 跨端契约（接口字段、参数、返回值）保持同步。
6. 安全与敏感信息：无密钥、生产配置、真实数据落库入库。

### 6.4 评审状态流转

```
草稿 → 待评审 → 评审中 → 通过/需修改（驳回）
                              ↓
                     修改后重新提交评审（Approval 可作废）
```

- 通过（Approval）后，由集成负责人执行合并。
- 未通过必须回复修改意见，不得静默合并。
- 评审意见闭环：Author 逐条回应，确认解决后方可推进。

### 6.5 质量控制指标

- MR/PR 应小而聚焦，单条原则上控制在可完整审阅的规模（大改动拆分为多个 MR）。
- 关键路径（研究流水线、数据模型、契约）改动必须双人评审。

## 7. 版本号管理规则

采用语义化版本（SemVer）`MAJOR.MINOR.PATCH`，配合预发布标签。

### 7.1 规则

| 版本位 | 变更触发 | 示例 |
| --- | --- | --- |
| MAJOR | 不兼容的 API/契约破坏性变更、里程碑切换 | 0.2.0 → 1.0.0 |
| MINOR | 向后兼容的新功能/能力 | 0.1.0 → 0.2.0 |
| PATCH | 向后兼容的缺陷修复 | 0.1.0 → 0.1.1 |

- 预发布阶段使用后缀：`-alpha.X`、`-beta.X`、`-rc.X`，如 `1.0.0-rc.1`。
- M1-M3 里程碑阶段保持 0.x（`0.1.0`、`0.2.0`、`0.3.0`），面向内部联调与契约验证；进入正式版后启用常规 MAJOR/MINOR/PATCH 递增。

### 7.2 版本号载体

- 版本号集中管理：前端以 `frontend/package.json` 的 `version` 为唯一载体；后端版本载体待 M1 落地时确定（服务于部署与 API 契约对齐）；契约文档头部版本字段须与两端保持一致。
- 每次发布在 release 分支上统一提升版本号，提交类型使用 `chore(release): bump to vX.Y.Z`。
- 通过 `git tag` 标记版本，如 `v0.2.0-rc.1`，标签指向发布合并提交。

### 7.3 发布流程

1. 从 `develop` 拉出 `release/vX.Y.Z`。
2. 冻结功能，仅接受修复与文档微调。
3. 提升版本号并补充变更记录（Changelog）。
4. 验证通过后 `--no-ff` 合并到 `main`，打标签。
5. 若无主版本变更，`main` 需同步回 `develop` 以避免版本回溯。

### 7.4 变更记录

- 维护根级或 `docs/` 下 `CHANGELOG.md`，按版本记录新增/修复/变更项。
- 变更项来源为合并后的提交信息（`feat`/`fix`/`refactor`/`breaking change`）。

## 8. 冲突解决机制

### 8.1 冲突预防

1. 按角色/模块划分目录责任（见 §2），减少同名文件交集。
2. 高频变动的契约文件（后端契约草案、接口类型）新增而非原地覆盖，必要时拆分文件。
3. 定期同步 `develop` 最新代码，缩短分支存活时间。

### 8.2 冲突处理规范

1. 冲突在个人工作分支上解决，禁止在共享分支（`main`/`develop`）直接改提交或强推解决冲突。
2. 处理流程：
   - `git fetch` 获取最新目标分支；
   - 将目标分支 rebase 或 merge 进当前分支触发冲突；
   - 手动合并冲突文件，保留双方合理改动；
   - 逐文件检查、本地构建/预检通过后提交，并重新运行相关测试。
3. 跨端或跨角色的语义冲突（如接口字段定义不一、契约与实现不一致），不得自行取舍，须在 MR 中说明并咨询契约持有方。
4. 冲突解决后更新 MR 描述，注明冲突涉及文件与处理结论，交付评审复验。

### 8.3 责任划分

- 提交者负责解决自身分支与目标分支的冲突。
- 集成负责人兜底协调共享分支的跨角色冲突裁定。

## 9. 分角色文件变更指南

### 9.1 开发（前端 Vue3、后端 FastAPI）

负责范围：`frontend/`、`backend/`、根级工程配置。

| 事项 | 要求 |
| --- | --- |
| 基分支 | 一律从 `develop` 拉取 `feature/*` |
| 提交类型 | `feat`/`fix`/`refactor`/`perf`/`test`/`build`/`style`/`chore` |
| MR 通过条件 | 构建通过 + 相关测试通过 + 评审通过 |
| 契约变更 | 后端先更新契约草案，前端其后承接；MR 互相引用 |
| 禁止事项 | 不提交依赖锁文件之外的生成物、不提交本地环境差异文件 |

### 9.2 产品

负责范围：`docs/prd/`、`docs/plan/`。

| 事项 | 要求 |
| --- | --- |
| 基分支 | 一律从 `develop` 拉取 `feature/product-{说明}`，变更经 MR/PR 合入 |
| 提交类型 | `docs`、`feat`（当新增需求说明）、`chore` |
| 评审 | 由产品负责人初评、研发/设计对照确认可落地性 |
| 变更记录 | 需求变更需关联《软件需求规格说明书》相应条目，标注版本与变更原因 |

### 9.3 设计

负责范围：`docs/design/`、`prototype/`。

| 事项 | 要求 |
| --- | --- |
| 基分支 | `develop` 上拉 `feature/design-{说明}` 或 `feature/proto-{说明}` |
| 提交类型 | `design`、`docs`、`feat`（当新增设计能力或原型页） |
| 评审 | 由设计负责人初评；原型交付前由研发确认可实现性与交互约束 |
| 契约衔接 | 交互规范修订后与后端契约、前端实现同步对齐，在 MR 中引用 |

### 9.4 跨角色协作通则

1. 所有变更均通过 MR/PR 进入共享分支，任何人不得绕过评审直接推送共享分支。
2. 变更涉及多角色领域时，MR 需包含对应角色的评审者。
3. 角色越权文件默认不合入（见 §2 范围对照），确需处理时描述原因。

## 10. 操作红线

角色与目录的职责边界见 §2，各角色提交/评审要求见 §9，冲突裁定见 §8.3。

### 10.1 日常操作红线

1. 不直接向 `main`/`develop` push 改动，一切经 MR/PR。
2. 不使用 `push --force` 改写共享分支历史；个人未合并分支视情况经团队同意方可强推。
3. 不合并未评审、未通过构建的 MR/PR。
4. 不提交密钥、生产环境凭据、真实敏感数据。
5. 损坏历史操作（`reset --hard` 到共享分支、`clean -f` 大范围删除）前必须确认并知会团队。

---

## 11. 质量审核与持续改进

1. 建立提交/分支/MR 的定期巡检，检查命名、信息格式与版本号合规性。
2. 引入可选 CI 门禁：提交信息格式校验、构建与测试自动触发，作为 MR 合并前置。
3. 出现规范漂移或不适用场景时，由集成负责人主持修订本规范，并全角色同步版本。
4. 本规范以 `vX.Y` 递增演进（与项目软件版本解耦），每次修订记录修订号与变更项。

## 12. 附：常用命令速查

| 用途 | 命令 |
| --- | --- |
| 拉取最新并创建功能分支 | `git checkout -b feature/xxx develop` |
| 查看本地分支与跟踪 | `git branch -vv` |

| 清理已合并分支 | `git branch -d feature/xxx` |
| 暂存冲突之外的改动 | `git add -u`（按需指定文件） |
