## 2. 接口一：POST /api/v1/intent/classify（意图判别）

### 2.1 请求

```
POST /api/v1/intent/classify
Authorization: Bearer <token>
Content-Type: application/json
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `text` | string | 是 | 1-2000 字符 | 用户在首页单入口的原始输入 |
| `force` | `"chat"` \| `"research"` \| null | 否 | 缺省 null | 手动强制路径（见 2.4），对应 PRD"强制闲聊/强制研究" |

请求示例：

```json
{ "text": "对比 Redis 和 Memcached 的适用场景" }
```

### 2.2 响应（200）

```json
{
  "intent": "research",
  "confidence": 0.93,
  "recommended_template": "generic",
  "recommended_tier": "standard",
  "estimated_token_budget": 150000,
  "estimated_cost_grade": "standard",
  "source": "llm",
  "degraded": false,
  "reason": "含明确可检索实体与对比意图，需多来源性能数据交叉核验"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `intent` | `"chat"` \| `"research"` \| `"uncertain"` | 判别结果，分流依据（见 2.3） |
| `confidence` | number（0-1） | 模型置信度；`source=forced/fallback` 时分别为 1.0 / 0.0 |
| `recommended_template` | string \| null | 研究推荐模板，当前恒为 `"generic"`；chat 路径为 null |
| `recommended_tier` | `"quick"/"standard"/"deep"/"extreme"` \| null | 推荐档位；chat 路径为 null |
| `estimated_token_budget` | number \| null | 该档位 token 预算，可直接用于"将走深度研究"提示；chat 为 null |
| `estimated_cost_grade` | string \| null | 成本档位键，值与 recommended_tier 一致；chat 为 null |
| `source` | `"llm"` \| `"forced"` \| `"fallback"` | 结果来源，见 2.4 |
| `degraded` | boolean | 是否保守降级（LLM 不可用/超时），为 true 时前端需显式提示 |
| `reason` | string | 一句中文判定依据，仅供排查/调试展示，不建议作为产品主文案 |

### 2.3 三种 intent 的产品分流口径（重要）

| intent | 前端动作 |
| --- | --- |
| `research` | 展示"将走深度研究"确认层（可带推荐档位与预估 token），用户确认后携带推荐参数走既有 `POST /api/v1/runs` 六阶段链路 |
| `chat` | 进入闲聊面板 `/assistant`，调用 `/assistant/chat` 流式直答，**不得**创建 run |
| `uncertain` | 产品上按"研究"处理（响应里带研究推荐参数，可直接发起 run），但建议提示"识别不太确定，已为你准备深度研究"，并给"改为直接聊聊"的入口（用 force=chat 重调） |

后端在任何失败场景都会保守收敛到研究路径（宁可多跑一次研究，不漏掉真实需求），因此前端不会因为模型故障无路可走。

### 2.4 source 与 force 语义

- `source=llm`：模型正常判别；
- `source=fallback` + `degraded=true`：LLM 未配置、调用失败或 8 秒超时。响应 intent 必为 research 且带研究参数。前端建议展示"智能判别暂不可用，已按深度研究为你准备"；
- `source=forced`：请求带了 `force`，模型被完全绕过（不产生 LLM 调用），confidence=1.0。用于确认层的两个撤回动作：
  - 用户在"将走深度研究"确认层点"直接聊聊" → 以 `force=chat` 重新请求；
  - 用户在闲聊回答后点"这是研究问题，深度研究一下" → 以 `force=research` 重新请求。

### 2.5 错误响应

| 状态码 | 场景 | 响应体 |
| --- | --- | --- |
| 401 | 未登录 / token 失效 | 统一错误信封 `{code, message, details}` |
| 422 | `text` 为空或超 2000 字符、`force` 取值非法 | FastAPI 校验错误结构 |

判别接口本身不返回 5xx 降级——模型故障在 200 响应里以 `degraded=true` 表达，前端无需为 5xx 做特殊分流。

## 3. 接口二：POST /api/v1/assistant/chat（闲聊 SSE 流式直答）

### 3.1 请求

```
POST /api/v1/assistant/chat
Authorization: Bearer <token>
Content-Type: application/json
Accept: text/event-stream
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `message` | string | 是 | 1-2000 字符 | 当前用户消息 |
| `history` | array | 否 | 最多 20 条（即最近 10 轮） | 客户端携带的近期对话，服务端不落库 |
| `history[].role` | `"user"` \| `"assistant"` | 是 | — | 发言角色 |
| `history[].content` | string | 是 | 1-4000 字符 | 消息内容 |

```json
{
  "message": "再展开说说",
  "history": [
    { "role": "user", "content": "什么是闭包" },
    { "role": "assistant", "content": "闭包是能记住定义时作用域变量的函数" }
  ]
}
```

### 3.2 SSE 响应帧协议

`Content-Type: text/event-stream`，UTF-8 编码，帧之间以空行分隔：

**增量帧**（多条，按回答顺序）：

```
data: {"delta":"闭包"}

data: {"delta":"就是能记住其定义时所在作用域变量的函数"}

```

注意 JSON 为紧凑格式（`{"delta":"..."}`，冒号后无空格）；片段可能是任意粒度（字/词/句），前端直接拼接即可。

**结束帧**（恰好一条，收到即结束）：

```
data: [DONE]

```

**错误帧**（流中断时出现，出现后不会再有 [DONE]）：

```
event: error
data: {"code":"provider_unavailable","message":"回答中断：RuntimeError"}

```

### 3.3 客户端实现提示（重要）

- **不要使用浏览器原生 EventSource**：EventSource 只支持 GET 且无法自定义 Authorization 头。请用 `fetch` POST + `ReadableStream` 手动按 SSE 格式解析（TextDecoder + 按 `\n\n` 切帧），鉴权照常走 Authorization 头；
- 解析规则：以 `data: ` 开头的行取负载；负载为 `[DONE]` 结束；`event: error` 行标记下一帧为错误；
- 建议在前端复用 M0 realtime 层的退避/关闭态经验，但 SSE 是一次性响应（非长连接频道），重连即重新发起请求（M2-1 服务端不保存回答上下文，刷新页面历史由客户端 localStorage 持有，与会话历史方案一致）。

### 3.4 错误响应

| 状态码 | 场景 |
| --- | --- |
| 401 | 未登录 / token 失效 |
| 422 | message 为空/超长、history 超 20 条或角色非法 |
| 503 | LLM 未配置（服务未接入模型时），统一信封 `code=provider_unavailable`，此为响应前错误，不是 SSE 帧 |

503 建议在打开闲聊面板或首次发送前做一次友好提示；正常联调环境不会出现。

## 4. 推荐前端流程（对齐前端 M2 方案 WP-9）

1. 用户在首页单入口输入并提交 → 调 `/intent/classify`（无 force）；
2. `research` → 确认层展示推荐档位与 `estimated_token_budget`，确认后调 `/runs`（body 可直接用 `recommended_template` / `recommended_tier`）；
3. `chat` → 跳转 `/assistant` 并发起 `/assistant/chat`，增量渲染回答；
4. `uncertain` → 等同 research，但文案体现"识别不确定"，提供 force=chat 撤回入口；
5. `degraded=true` → 同 research 流程，额外展示降级提示；
6. 两个方向都提供互改入口（force 重调），撤回后不保留对方链路的副作用（classify/chat 均不产生项目数据）。

## 5. 后端非目标（M2-1 明确不做，避免前端等待）

- 无服务端会话/历史存储：闲聊历史是客户端态，接口无会话 ID、无历史拉取端点；
- 意图判别结果不做服务端审计留档（完整版审计在 M2 后续工作包）；
- 闲聊不做联网检索、不引用来源；系统提示已约束模型在遇到实时性问题时建议用户改走深度研究；
- OpenAPI M2 契约文件按 M1 节奏在 M2 收口联调前统一导出（当前以本文档为准）；
- 没有 `/intent/classify` 的批量版本。

### 8.2 浏览器全链路验证（经 Vite 代理，真实后端）

| 路径 | 结果 |
| --- | --- |
| research（"对比 Redis 和 Memcached…"） | 确认层展示推荐 standard 档、预估 150,000 token；确认后跳向导，档位与问题原文均自动预填 |
| chat（"你好呀，你是谁"） | 直达 `/assistant` 自动发问，流式逐字渲染，完整收尾无报错 |
| 多轮闲聊（第二轮手动发问） | history 携带正确，回答正常 |
| uncertain / degraded | 前端按 §2.3 收敛研究路径，确认层文案区分"意图不确定 / 判别暂不可用"，降级时保留"改为直接聊聊"（force=chat）入口 |
| 闲聊后互改（force=research） | 回首页自动出确认层；长/短问题两档对照（standard/150,000、quick/50,000）均正确 |
| 确认层撤回（force=chat） | 跳助手面板自动发问并流式回答成功 |
| 强制闲聊旁路（研究类问题点"直接聊聊"） | 不创建 run、不进向导，由模型直答 |

全程零控制台错误、零非预期 4xx/5xx，网络面板确认闲聊/撤回路径无 `POST /runs`（无项目数据副作用，符合 §4 第 6 条）。

### 8.3 问题记录（均为前端侧缺陷，已在 `0460c15` 修复，无需后端处理）

1. **当前用户消息重复进入 history**：前端先压入用户消息再截取 history，而后端 `_build_messages` 为 `history + 当前 message` 拼接，导致每个问题重复发送。已改为压入前截取。
2. **失败重发重复展示用户气泡**：resend 原实现再次走 send 插入新用户消息。已改为复用原用户气泡、仅重建助手气泡，且重发 history 截到该用户消息之前。
3. **force=research 自动确认层档位错配**：助手面板"深度研究这个问题"进入首页的自动判别分支未回填 `recommended_tier`，长问题场景出现"quick 档 + 150,000 token"矛盾并把错误档位带入向导。已与手动发送路径统一回填（推荐为空时兜底 quick）。
4. **向导不预填问题**：研究确认层跳 `/wizard` 未携带问题原文。已通过 query `q` 预填（经长度校验，仍可修改）。
