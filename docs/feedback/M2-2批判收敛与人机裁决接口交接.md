## 2. REST 契约（已冻结，逐字段见 openapi-m2-2.json）

### 2.1 GET `/api/v1/runs/{run_id}/conflicts`

- 200：`ConflictResponse[]`，按 `created_at` 升序；run 不存在/非本人 → 404。
- 前端已有 `getRunConflicts(runId)`（`src/services/api/dashboard.ts:51`），**路径与响应结构均无需改**。

### 2.2 GET `/api/v1/conflicts/{conflict_id}`

200 返回 `ConflictDetailResponse`（在列表项字段上**多两个内嵌对象**）：

```jsonc
{
  // …ConflictResponse 全部字段…
  "evidence_a": {
    "id": "01M2…",
    "title": "国家统计局报告",
    "url": "https://stats.gov.cn/x",
    "domain": "stats.gov.cn",
    "snippet": "新增装机 210GW……",
    "credibility": "A",
    "source_type": "news",
    "published_at": "2026-09-01T00:00:00Z"   // 可空
  },
  "evidence_b": { /* 同构八项 */ }
}
```

- 现有 `getConflict()`（`dashboard.ts:56`）声明的返回类型是 `ConflictResponse`，**需改为 `ConflictDetailResponse`**（见 §3.2）。
- 当前 `ConflictBlock.vue` 由页面从证据池按 `evidence_a_id/evidence_b_id` 反查证据传入（`CockpitView.vue:343`）。后端详情已内嵌摘要，两种用法都合法：
  - **推荐（省事）**：展开单条分歧时调 `getConflict(id)`，直接用 `evidence_a/evidence_b`，不再依赖证据池是否已加载；
  - 保留现状（证据池反查）也可正常工作，属于后端超集增量，不阻塞本次联调。

### 2.3 POST `/api/v1/conflicts/{conflict_id}/verdict`

请求体（JSON）：

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `choice` | `'evidence_a' \| 'evidence_b' \| 'both' \| 'reject'` | 是 | 强枚举，非法值 422 |
| `reason` | `string` | 是 | **strip 后不能为空串**，纯空白 422；上限 2048 |
| `additional_note` | `string \| null` | 否 | 纯空白服务端归一为 null；上限 2048 |

200 响应：

```json
{ "conflict_id": "01M2…", "status": "resolved", "verdict_id": "01M2…" }
```

错误响应（经现有 `http.ts` 归一后为 `ApiError`，`status`/`code`/`detail` 直接可用）：

| 场景 | HTTP | `ApiError.code` | 说明 |
| --- | --- | --- | --- |
| 无 token / token 失效 | 401 | `auth_error` | http 层自动刷新重放，无需页面处理 |
| run/分歧不存在或非创建者 | 404 | `not_found` | 提示「分歧不存在」即可 |
| choice 非四值 / reason 纯空白 | 422 | `HTTP_422` | FastAPI 校验体 `detail` 为数组，`http.ts` 已 `JSON.stringify` 兜底；页面建议对 reason 空值做**前端前置校验**，422 仅兜底展示 |
| 冲突已 resolved/abandoned 重复提交 | 409 | `conflict` | **重点**：提交成功后禁用按钮；收到 409 提示「该分歧已裁决」并刷新列表 |

### 2.4 自动恢复时序（无「继续」按钮，别加）

1. high 冲突未全部裁决时 run 一直 `paused@critique`，期间每条 POST 都 200，但不恢复；
2. **该 run 最后一条 `awaiting_human` 被裁决后**，后端在响应返回后自动起后台任务恢复（经 PostgresSaver），run 自行 `running → succeeded`；
3. 前端节奏：每次 POST 200 后按现有 run 轮询/WS 订阅等 `run.finished(status=succeeded)` 即可，**不需要也不存在「继续研究」接口**；
4. 恢复后报告 `GET /runs/{id}/report` 的「冲突与不确定性 → 分歧与局限」段会含议题、双方来源链接、裁决意见/理由/局限备注。

## 6. 已知边界与 FAQ

1. **为什么 mock 里原来的 performance_data 不能保留？** 后端 Conflict.type 是强枚举列（16 字符 String + Pydantic Literal），落库/响应只可能是四值之一；保留该值会在切真实接口后出现前端标签映射缺键。
2. **reason 为什么要前端再校验一次非空？** 纯空白在后端是 422（FastAPI 校验在进入业务前），前端前置拦截体验更好；422 的 detail 是字段数组而非字符串，直接展示会是 JSON 文本。
3. **提交裁决后要乐观更新吗？** 建议乐观把该行置为「已裁决」并禁用操作；最终状态以 200 响应的 `status` 与随后列表/WS 为准；409 时回滚并提示已被裁决。
4. **run 没有及时变 succeeded？** 末条裁决后恢复是后端 `asyncio.create_task` 后台执行（LLM 续跑需要数秒到数十秒），以 `run.finished` 帧/轮询为准，不要在 POST 200 的当帧就期待 succeeded。
5. **created_at/updated_at 为何可空？** 类型上可选以兼容历史行与 WS 子集帧；列表接口实际都会返回 ISO8601 字符串。
6. **冲突被自动收敛（low/medium）前端能看到吗？** 不会收到 conflict.detected 帧（只推 high），列表里能查到 status=resolved 的行；报告中只进一句收敛摘要，不进待办区。
