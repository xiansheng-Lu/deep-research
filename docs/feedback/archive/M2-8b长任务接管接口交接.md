## 0. 本次对接结论（TL;DR）

1. **执行位置迁移，协议不变**：研究首跑/恢复改由独立 worker 进程经 Celery 队列驱动，实时事件改走 Redis Pub/Sub 跨进程扇出到 API 的 WS 端点。前端连接的 `ws://localhost:8000/api/v1/ws/runs/{id}/stream`、全部帧名/载荷、REST 路径与请求体**零变化**。
2. **前端运行代码预期零改动**：`useRunStream`/看板/报告页无须为 b 段改代码。
3. **唯一新增语义**：pause 一个「执行进程已失联、等待自动清扫」的 run 时，409 响应 `details.code` 新增 **`RUN_ORPHAN_RECOVERING`**（HTTP 状态仍 409；M2-8b 前该场景返回 `RUN_NOT_PAUSABLE`）。前端可不识别（走现有 409 提示即可），建议识别后提示「任务执行状态异常，系统正在自动恢复，请刷新后重试」。
4. **联调形态变为三进程**：PG + Redis（docker 栈）与主机上的 **uvicorn + Celery worker 两个常驻进程**。worker 不在线时新 run 会停在 `pending`（任务在队列无人消费），回归前务必确认 worker 已启动（见 §1）。
5. 联调先执行 **`alembic upgrade head`（head 0006 → 0007）**；新增配置均有默认值（`WORKER_ENABLE_REDIS=true` 等），.env 已含 Redis 连接时无需额外设置。

## 2. 契约影响（openapi-m2-8，仍 27 路径）

### 2.1 REST：路径/请求体/响应零变化

- `POST /runs`、`POST /runs/{id}/pause|cancel|resume|intervene`、全部 GET 端点行为与 M2-8a 一致。
- 唯一差异是 pause 孤儿场景的 `details.code`（见 §2.2）；其余错误码（`RUN_NOT_PAUSABLE`/`RUN_ALREADY_PAUSED`/`RUN_NOT_RESUMABLE` 等）口径不变。
- 响应时序：因任务经队列投递给 worker，`POST /runs` 201 后 run 在 `pending` 停留到 worker 取任务（本机实测约 10-15s 冷启动，热任务更快），随后翻 `running`；前端既有「pending/running 看板等待 + WS/轮询收敛」逻辑天然兼容，无需新增轮询或超时假设。

### 2.2 pause 新增 details.code：RUN_ORPHAN_RECOVERING

| 场景 | HTTP | code | 前端建议 |
| --- | --- | --- | --- |
| running 且 worker 租约新鲜（正常在途） | 200 | - | 既有暂停流程 |
| 非 running / 内存态孤儿 | 409 | `RUN_NOT_PAUSABLE` | 既有提示 |
| running 但执行租约过期（worker 失联，等待/正在清扫） | 409 | **`RUN_ORPHAN_RECOVERING`** | 提示「任务执行状态异常，系统正在自动恢复，请刷新后重试」；不识别时走现有 409 文案也不破坏功能 |

该码只在 worker 崩溃且租约过期（默认 >90s 未心跳）的罕见场景出现，正常回归中可遇而不可求；后端已用真链+单测验证，前端不做专项构造亦可关闭。

## 3. WS 帧

- 帧名、载荷、envelope（v/event_id/ts/run_id/stage/type/payload）、ping/pong、终态即断：**全部不变**。
- 传输路径由「worker 同进程直投」变为「worker → Redis Pub/Sub → API 桥接协程 → WS」；前端无感知。后端真链已验证跨进程下 stage.* / sub_question.* / evidence.fetched / token.usage.update / interrupt.requested / conflict.* / run.finished 全帧不丢不重（同节点本地直投 + 跨节点桥接，origin 去回环）。
- 终态兜底不变：事件偶发丢失仍以 REST 轮询/重连初帧收敛。

### 5.1 观察项（不阻塞关闭）

1. **worker 冷启动 10-15s**：worker 依赖为任务级装配（方案 §23.2 偏差 2，方案允许的形态），每个 Celery 任务首次建连/导入约 10-15s 后 run 翻 running（WSL drvfs 下 LLM provider 模块首次导入占大头）；连续任务、容器/ext4 部署更快。功能与时序正确性不受影响，前端等待态已有覆盖。进程级常驻 loop 池化为后续优化项。
2. **清扫时机**：worker 在「每个子进程第一个任务执行前」扫一次（非进程启动即刻，方案 §23.2 偏差 1）；即 worker 重启后第一个 run 投递时先收敛历史孤儿再执行。前端唯一可感知面仍是 §2.2 的 409 code。
3. **prefork 重定向日志**：后台文件方式跑 worker 时子进程 structlog 日志可能不显示（MainProcess 的 received/ready 正常）；容器部署 stdout 由 Docker 收集。排查以 run 行 execution_owner/lease_until、Redis 键与 WS 帧为准。
