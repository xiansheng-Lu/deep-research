### P0-1 Vite 开发代理未转发 WebSocket，指挥舱实时阶段永久不动（M1 验收阻断项）

**现象**

点击"启动研究"跳转指挥舱后，页面永久显示"等待中 阶段 -/6 Token 0 / 50000"，六个阶段全部为"待执行"；研究实际约 6-10 秒已成功结束，但页面不更新、不出现"查看报告"按钮。手动刷新后，仅凭一次 REST 快照即可正确显示"已完成 6/6"与全部阶段状态，说明阶段渲染逻辑本身正确，问题仅在实时通道。

浏览器实测：Network 面板中 WS 握手无 101 Switching Protocols，`readyState` 恒为 0（CONNECTING）；同一 token 直连 `ws://localhost:8000/api/v1/ws/...` 可立即 open，排除后端问题。

**位置**

- `frontend/vite.config.ts` 第 45 行：`/api` 代理规则缺少 `ws: true`
- WS 地址由 `frontend/src/services/api/runs.ts` 第 25-29 行 `buildRunStreamUrl` 构成为 `/api/v1/ws/runs/{id}/stream`，命中 `/api` 规则
- 第 46 行配置了 `ws: true` 的 `/ws` 规则没有任何请求使用（前缀不匹配）

**根因**

Vite 代理规则默认只转发 HTTP；`/api` 规则未开启 WebSocket 升级转发，经 5173 端口的 WS 握手无法到达 8000 后端。

**修复（一行）**

```ts
// frontend/vite.config.ts 第 45 行
'/api': { target: apiBase, changeOrigin: true, ws: true },
```

顺带修正 `frontend/src/services/api/runs.ts` 第 24 行的过时注释（"dev 环境由 Vite 代理 /ws 前缀"应改为"/api 前缀，dev 代理已开启 ws 转发"）。

**验收标准**

重启 `pnpm dev` 后，用快速档发起一个语义明确的研究问题（约 6-10 秒跑完），不刷新页面即可看到六个阶段（澄清界定 / 问题分解 / 证据检索 / 证据标准化 / 交叉审校 / 报告撰写）依次点亮，结束后自动出现"查看报告"入口。

建议分支：`feature/frontend-ws-proxy-m1`。

> **修复回填（前端，2026-09-12，已合入 dev `4ba10fe`）**
>
> - 已按建议修复：`/api` 规则增加 `ws: true`；同时删除无任何请求命中的 `/ws` 死规则及派生变量 `wsBase`（WS 实际地址 `/api/v1/ws/...` 只命中 `/api`，避免后续误判）。

### P0-2 WebSocket 建连无超时，connecting 态对用户完全静默（健壮性，建议同批修复）

**现象**

当 WS 握手无响应（P0-1 场景、网络抖动或代理异常）时，浏览器不触发 `onclose`，指数退避重连永远不会启动；通道停留在 `connecting` 态，而指挥舱仅对 `retrying` 态有提示文案；`useRunStream` 又只在通道变为 `live` 后补一次 REST 请求，没有轮询兜底。最终表现为页面无任何提示地永久等待，用户只能手动刷新。

**位置**

- `frontend/src/services/realtime/realtime.ts` 第 101-134 行：`WsChannel.connect` 无连接超时
- `frontend/src/composables/useRunStream.ts` 第 208-212 行：仅 `live` 时执行一次 `alignWithRest`
- `frontend/src/views/cockpit/CockpitView.vue` 第 131-137 行：断线提示仅判断 `channelState === 'retrying'`

**修复建议（两项可都做）**

1. 在 `WsChannel.connect()` 增加连接超时计时器：建议 8-10 秒未收到 `onopen` 则主动关闭并转入 `scheduleReconnect()`（进入 `retrying` 态）；在 `onopen` / `onclose` / `disconnect` 中清除该计时器，避免泄漏。
2. 在 `useRunStream` 对非终态 run 增加兜底 REST 轮询（建议每 3-5 秒调用一次 `getRun`，收到终态后停止并销毁通道）；或至少在 connecting 超时时于指挥舱展示"实时连接建立中…"提示与手动重试入口。CockpitView 的提示条件从仅 `retrying` 扩展到 `connecting`，两种状态使用不同文案。

**验收标准**

后端停止或 WS 被拦截时，指挥舱在 10 秒内出现明确提示，并能通过自动重连或 REST 轮询收敛到终态；不允许出现无提示的永久等待。

> **修复回填（前端，2026-09-12，已合入 dev `4ba10fe`）**
>
> 建议两项均已落地：
>
> 1. `WsChannel.connect()` 增加 10 秒握手超时（`connectTimeoutMs` 可配，默认 10000ms）：超时未 `onopen` 时摘除事件回调、主动关闭 socket 并转入既有指数退避重连（进入 `retrying` 态）；计时器在 `onopen` / `onclose` / `disconnect` / 超时回调中全部清除，无泄漏。
> 2. `useRunStream` 对非关闭态 run 增加 4 秒兜底 REST 轮询（`getRun` 快照），收到 succeeded/failed/cancelled/paused 任一关闭态即停止轮询并销毁通道；指挥舱提示从仅 `retrying` 扩展为 `connecting`（"实时连接建立中，阶段状态通过同步接口持续跟踪…"，品牌色）与 `retrying`（"实时连接中断，正在自动重连…"，警示色）两种文案。
>
> **实测**：paused 态指挥舱网络记录在初帧 GET 后完全静止（无 WS 长连、无轮询请求累积），关闭态收敛正确；连接超时路径因后端与代理均正常未做故障注入实测，逻辑经类型检查与代码走查确认，建议共同回归时由后端停服场景补充一次实证。
> - 结论：**已修复，自测通过，待共同回归补充故障注入实证**。

### P0-3 澄清挂起（paused）的 run 被前端误渲染为"已完成"（联调新发现，前端侧已修复）

**发现方式**：前端在 P0-1 修复后做真实链路回归时发现——经页面正常发起的 run，指挥舱实时显示"已完成 6/6 / 查看报告"，但点开报告页却显示"报告尚未生成（已暂停，当前阶段：澄清界定）"；REST `GET /runs/{id}` 与数据库核实，run 真实状态均为 `paused / current_stage=clarify`。

**根因（契约对齐问题，非后端缺陷）**

后端在澄清挂起（HITL）时同样发布 `run.finished` 事件，但负载 `status="paused"`（见 `backend/app/orchestrator/executor.py` 第 411-435 行：无报告产出即置 paused 后统一发 run.finished）。前端实时类型 `RunFinishedPayload.status` 早已包含 `paused`，但 `useRunStream.handleRunFinished` 无条件按 `succeeded` 写状态，导致：

- 指挥舱显示"已完成 6/6"并出现虚假的"查看报告"入口（报告接口实际返回 422）；
- 状态与报告页、REST、数据库三处事实矛盾，用户会误判研究成功。

**修复（dev `4ba10fe`）**

- `handleRunFinished` 改为信任事件负载：`applyTerminalPayload(payload, payload.status)`，不再硬编码 succeeded；
- paused 与三种终态一并归入"通道关闭态"集合：不建 WS、不启动兜底轮询（paused 不会再产生实时事件，M1 冻结契约也无恢复端点）；
- 指挥舱为 paused 增加警示引导卡："研究已暂停：等待澄清确认"，说明系统在澄清界定阶段需要补充信息、M1 暂未提供页面恢复入口、可重新发起并把问题描述得更明确；不再出现"查看报告"按钮。

**实测**

- 修复前：本次 4 个 paused run（含 1 个经 UI 全流程发起）全部被误显"已完成"，反证缺陷稳定复现；
- 修复后：同一批 paused run 重开指挥舱，正确显示"已暂停 阶段 1/6 Token 真实用量"，网络面板仅 1 次初帧 GET，无 WS 长连、无轮询；
- 既有 succeeded run（后端冒烟样本）指挥舱 6/6、报告页四段渲染均无回退。

**验收标准**：paused run 在指挥舱显示"已暂停"与澄清引导、不出现查看报告入口；succeeded run 行为保持不变。

**结论：已修复，自测通过，待共同回归。**

> 备注：paused 之后的"恢复研究 / 回答澄清问题"交互不在 M1 冻结契约内（OpenAPI 无相关端点），按文档范围留待 M2；本单仅修复状态误判与用户告知。

### 8.4 联调环境处置记录（供运维参考）

联调初期登录接口间歇 500、三容器反复"Up Less than a second"。根因是 **WSL2 空闲自动关闭，systemd 托管的 Docker 容器随之停止并形成约 30 秒一轮的重启循环**（非 OOM、非配置错误，PG 就绪后登录即恢复）。处置：后台常驻 `wsl -d Ubuntu -e sleep infinity` 保活，之后 PostgreSQL / Redis / MinIO 持续 healthy，接口恢复稳定。该保活进程当前仍在运行。
